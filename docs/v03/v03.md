# V0.3 — Validated Predictive Projection Layer

> **Status:** Planned  
> **Prerequisite:** V0.2.5 historical evaluation foundation.  
> **Primary objective:** Build the first validated, point-in-time predictive projection system for EuroLeague Fantasy.

## 1. Objective

V0.2 established deterministic decision support.

V0.2.5 established the historical laboratory needed to measure whether those decisions work.

V0.3 should establish the first **validated predictive projection layer**.

Core pipeline:

```text
historical/current information
        ↓
P(play)
        ↓
E(minutes | play)
        ↓
E(FP/min | play)
        ↓
E(fantasy points)
        ↓
calibration + uncertainty
        ↓
player valuation
        ↓
V0.4 optimizer
```

The key architectural rule is:

> **Do not make one model learn availability, playing time, and performance as one undifferentiated target.**

## 2. Definition of done

V0.3 is complete when:

- [ ] Availability is modelled explicitly.
- [ ] Expected minutes are modelled separately.
- [ ] Conditional performance is modelled for players who play.
- [ ] Final expected fantasy points combine the components coherently.
- [ ] HC prediction remains a separate target family.
- [ ] All features are point-in-time safe.
- [ ] V0.2.5 baselines remain available for comparison.
- [ ] Evaluation covers multiple historical seasons.
- [ ] Model differences include uncertainty / paired comparisons.
- [ ] Calibration is fit without test-set leakage.
- [ ] Basic prediction uncertainty is available.
- [ ] Oracle lineup regret is available or explicitly deferred.
- [ ] Every prediction is reproducible and traceable.
- [ ] Leakage and replay tests are comprehensive.

## 3. Guiding principles

### 3.1 Baselines remain mandatory

Every V0.3 model must be compared against:

- `season_mean`
- `last3`
- `last5`
- `last10`
- `ewma`
- `xpdk_v02`

A more complex model is useful only if out-of-sample evidence justifies the added complexity.

### 3.2 Do not optimize for MAE alone

Track:

- MAE/RMSE;
- bias;
- Spearman;
- Top-K recall;
- Value Spearman;
- lineup score;
- captain regret;
- other decision metrics.

Different metrics can favor different models. V0.3 should therefore avoid declaring a single universal “best model”.

### 3.3 Separate prediction from decisions

V0.3 answers:

> What should we expect this player to score?

V0.4 answers:

> Given those projections, budget and roster constraints, what should we do?

Keep optimizer logic out of the predictive layer.

### 3.4 Prefer interpretable improvements first

Recommended order:

1. calibrated xPDK;
2. availability + minutes + production decomposition;
3. regularized regression/tree models if justified;
4. ensemble only if validation shows complementary signal.

Do not jump directly to deep learning.

## 4. Phase A — Harden the evaluation laboratory

### 4.1 Multi-season evaluation

Support:

- E2022
- E2023
- E2024
- E2025

Required experiment modes:

**Within-season walk-forward**

```text
information before round r → predict round r → compare with round r
```

**Cross-season**

```text
E2022 + E2023 + E2024 → test E2025
```

**Rolling cross-season**

```text
E2022 → E2023
E2022+E2023 → E2024
E2022+E2023+E2024 → E2025
```

All windows should be configurable.

### 4.2 Paired model comparisons

For model pairs, calculate:

- ΔMAE;
- ΔRMSE;
- ΔSpearman;
- ΔTop-K recall;
- ΔValue Spearman;
- Δlineup score;
- Δcaptain regret.

Prefer paired player/round observations.

Add bootstrap confidence intervals or another appropriate paired uncertainty estimate.

The purpose is to determine whether an improvement is consistent enough to justify complexity—not to manufacture a universal ranking.

### 4.3 Sample-size reporting

Every aggregate result should expose, where applicable:

- players;
- active players;
- rounds;
- games;
- price observations.

## 5. Phase B — Availability model

Estimate:

```text
P(play in round | information available before cutoff)
```

### Target

Retain explicit states:

- played;
- available but DNP;
- questionable;
- inactive/out;
- unknown.

Initial predictive target can be:

```text
played = 1
did_not_play = 0
```

### Features

Only point-in-time features:

- recent appearance rate;
- rolling DNP rate;
- minutes volatility;
- minutes trend;
- historical availability/injury status where actually available;
- roster status;
- team;
- opponent;
- round context;
- double-round week;
- rest;
- schedule density;
- starter rate;
- recent role;
- transfer/team-change state where available.

### Initial models

Start with:

1. historical availability rate;
2. rolling availability rate;
3. logistic regression;
4. optionally a calibrated tree model.

Measure:

- log loss;
- Brier score;
- calibration;
- ROC-AUC as secondary;
- fantasy-relevant precision/recall.

Probability calibration matters more than raw classification accuracy.

## 6. Phase C — Minutes model

Estimate:

```text
E[minutes | player plays, cutoff]
```

### Baselines

- season mean;
- last3;
- last5;
- last10;
- EWMA;
- starter-conditioned minutes;
- availability-conditioned minutes.

### Candidate features

- recent minutes;
- EWMA minutes;
- minutes standard deviation;
- starter rate;
- recent starts;
- DNP rate;
- rotation depth;
- role;
- rest;
- double-round week;
- opponent;
- home/away.

### Evaluation

Report:

- MAE;
- RMSE;
- median absolute error;
- bias;
- rank correlation;
- interval calibration if intervals are introduced.

## 7. Phase D — Production-per-minute model

For players who play, estimate:

```text
E[fantasy_points / minute | player plays, cutoff]
```

Possible targets:

- FP/min;
- PIR/min;
- component-level production.

### Candidate approaches

**Model 1 — rate baseline**

```text
EWMA(FP/min)
```

**Model 2 — stabilized rate**

Shrink toward:

- career rate;
- season mean;
- positional prior;
- team/role prior.

**Model 3 — regularized regression**

Potential features:

- recent FP/min;
- recent PIR/min;
- points/min;
- rebounds/min;
- assists/min;
- steals/min;
- blocks/min;
- turnovers/min;
- shooting efficiency;
- free-throw rate;
- position;
- team;
- opponent defensive strength;
- home/away;
- rest;
- role.

Use regularization because individual player samples can be small.

## 8. Phase E — Fantasy-point composition

First-order formulation:

```text
E[FP] =
    P(play)
    × E[minutes | play]
    × E[FP/min | play]
```

Where useful, use component-level prediction:

```text
expected points
+ expected rebounds
+ expected assists
+ expected steals
+ expected blocks
- expected turnovers
+ expected bonuses
```

The deterministic fantasy scoring layer remains the single source of truth for scoring rules.

Prediction code must not duplicate scoring rules ad hoc.

## 9. Phase F — Calibration

The V0.2.5 benchmark showed systematic xPDK level bias in the reported E2025 R1–12 sample.

Test simple calibration before complex modelling.

### Candidates

**Intercept**

```text
actual = prediction + b
```

**Linear**

```text
actual = a + b × prediction
```

**Multi-model**

```text
actual =
    a
  + b1 × xpdk_v02
  + b2 × ewma
  + b3 × season_mean
```

Use regularization if needed.

### Leakage rule

For round `r`, calibration parameters must be fitted only on data before `r`.

Never fit calibration on the reported test target.

### Evaluation

Compare raw and calibrated predictions against all V0.2.5 baselines on unseen rounds.

## 10. Phase G — Uncertainty

V0.3 should produce more than a point estimate.

Target output:

```text
expected fantasy points
lower bound
upper bound
prediction spread
```

Start with empirical out-of-sample residual distributions.

Possible segmentation:

- position;
- minutes bucket;
- availability state;
- model family.

Do not over-segment early.

Uncertainty is important because two players with equal expected value can have very different risk profiles.

## 11. Phase H — Oracle and decision metrics

### Oracle lineup

For each historical round:

```text
oracle = highest-scoring legal lineup using realized outcomes
regret = oracle score - model-selected lineup score
```

This is more informative than raw selected-lineup score alone.

### Captain

Measure the difference between the selected captain and the best legal realized captain.

### Sixth man / bench / formation

Apply the same principle while respecting actual fantasy rules.

These are decision-layer metrics, not training targets for the player model.

## 12. Phase I — Value projection

Once expected points are validated, expose:

```text
expected fantasy points / fantasy price
```

Also consider:

- points above replacement;
- positional replacement value;
- expected value change;
- risk-adjusted value.

Keep full transfer optimization for V0.4.

## 13. Phase J — Cold starts

Use an explicit fallback hierarchy:

```text
current-season player history
        ↓
previous-season player history
        ↓
career history
        ↓
position prior
        ↓
team/role prior
        ↓
league-wide prior
```

Every prediction should expose `fallback_source`.

This allows early-round and data-rich predictions to be evaluated separately.

## 14. Phase K — Diagnostics

For interpretable models, expose coefficients/contributions.

Diagnostics should test whether these feature families add out-of-sample signal:

- recent form;
- EWMA;
- minutes volatility;
- opponent strength;
- position-specific opponent defence;
- rest;
- double-round context;
- previous-season information.

Do not add features merely because they are available.

## 16. Suggested package architecture

Extend the current evaluation architecture:

```text
src/euroleague_fantasy_manager/
    evaluation/
        dataset.py
        features.py
        targets.py
        baselines.py
        metrics.py
        backtest.py

    prediction/
        __init__.py
        availability.py
        minutes.py
        production.py
        fantasy_points.py
        calibration.py
        uncertainty.py
        registry.py

    valuation/
        __init__.py
        player_value.py
```

Keep deterministic fantasy rules separate.

Do not put prediction logic inside:

- lineup optimizer;
- trade optimizer;
- CLI;
- API ingestion;
- scoring/rules code.

## 19. Testing strategy

### Unit tests

Cover:

- availability targets;
- minutes targets;
- production targets;
- FP decomposition;
- calibration;
- uncertainty;
- fallback hierarchy;
- serialization;
- deterministic prediction.

### Leakage tests

Create fixtures where future:

- games;
- player statistics;
- prices;
- roster changes

are added after the cutoff.

The prediction before the cutoff must remain unchanged.

### Historical replay

For identical:

```text
dataset + cutoff + model configuration
```

predictions must be identical unless randomness is explicitly part of the model.

### Regression tests

Keep V0.2.5 baseline outputs available so new changes cannot silently degrade the historical benchmark.

## 20. Recommended experiment order

Do not implement everything simultaneously.

1. Re-run V0.2.5 baselines across multiple seasons.
2. Calibrate xPDK.
3. Build availability model.
4. Build minutes model.
5. Build production-per-minute model.
6. Combine availability × minutes × production.
7. Calibrate the combined model.
8. Add uncertainty.
9. Add oracle lineup/regret evaluation.
10. Test regularized ML models against the decomposed model.
11. Test ensembles only if individual models provide complementary signal.

## 21. Explicitly out of scope

Do not turn V0.3 into the optimizer release.

Defer:

- multi-transfer optimization;
- long-horizon transfer planning;
- full bankroll optimization;
- GUI;
- LLM recommendations;
- automatic lineup submission;
- live injury-news scraping;
- deep learning;
- reinforcement learning;
- large Monte Carlo season simulation.

These belong to later milestones.
