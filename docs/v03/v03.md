# V0.3 — Predictive Quantitative Architecture

> **Architectural design document.**
>
> V0.3 is the first release where `euroleague_fantasy_manager` should move from heuristic projection toward a statistically grounded prediction stack.
>
> V0.3 must be built on the V0.25 evaluation framework. A more complex model is not considered an improvement unless historical walk-forward evaluation demonstrates that it improves the relevant decision metrics.

---

# 1. Objective

V0.3 transforms the current V0.2:

```text
recent fantasy average
+ price prior
+ heuristic availability
+ heuristic FDR
+ heuristic win probability
```

into a structured prediction pipeline:

```text
historical point-in-time data
            ↓
expected availability
            ↓
expected minutes
            ↓
component production rates
            ↓
game-context adjustments
            ↓
expected PIR / fantasy points
            ↓
uncertainty distribution
            ↓
valuation / capital-gain layer
            ↓
optimizer
```

The key architectural change is that **performance prediction, valuation, and decision optimization become separate layers**.

---

# 2. Design principles

## 2.1 Predict components before decisions

The model should not directly learn:

```text "start player X"
```

It should estimate:

```text probability of playing
expected minutes
expected production
expected fantasy points
uncertainty
```

The optimizer decides what to do with those estimates.

## 2.2 Keep hard rules deterministic

No model can override:

- budget;
- roster composition;
- club limit;
- legal formations;
- captain restrictions;
- turn lockouts;
- trade limits;
- selling-price rules.

The validator remains authoritative.

## 2.3 Preserve the V0.2 baseline

The V0.2 xPDK remains available as:

```text xpdk_v02_baseline
```

It must never disappear.

Every V0.3 model should be evaluated against it.

## 2.4 Point-in-time correctness is mandatory

All training and inference data must respect the decision cutoff.

No future:

- scores;
- player statistics;
- prices;
- injuries;
- statuses;
- derived results.

## 2.5 Model complexity must earn its place

A new model is accepted only if it improves out-of-sample performance or a clearly defined decision metric.

# 4. Prediction stack

## 4.1 Layer 1 — availability

Estimate:

```text
P(play)
```

Inputs may include:

```text
current status
starter/bench status
historical participation
recent DNP
recent minutes
team depth
injury/status indicators when available
```

Output:

```text
play_probability
```

Do not use the final fantasy projection to hide availability.

---

# 5. Layer 2 — expected minutes

Estimate:

```text
E[minutes | player plays]
```

Potential features:

```text
recent minutes
season minutes
starter probability
recent starts
team rotation depth
coach usage
back-to-back / double-week context
rest
foul trouble history
recent availability
```

This is likely to be one of the most valuable V0.3 components.

A player who scores 1.0 fantasy point per minute but is projected for 12 minutes should not be treated like a player projected for 30 minutes.

---

# 6. Layer 3 — component production

Estimate per-minute or per-possession production for:

```text
points
rebounds
assists
steals
blocks
fouls drawn
turnovers
missed shots
```

Potential derived rates:

```text
PTS / minute
REB / minute
AST / minute
STL / minute
BLK / minute
FD / minute
TOV / minute
```

This allows the model to separate:

```text
role/playing time
```

from:

```text
production while on court
```

---

# 7. Layer 4 — matchup/context

The model can incorporate:

```text
home/away
opponent strength
team strength
FDR
rest
schedule congestion
double-week
expected team margin
expected game total / scoring environment if available
```

The V0.2 FDR should initially remain available as a feature.

Do not automatically replace it with a learned model until evaluation proves that the learned matchup representation is better.

---

# 8. Layer 5 — expected fantasy score

Calculate expected fantasy score from component predictions using the deterministic fantasy scoring formula.

Conceptually:

```text
expected_minutes
        ×
expected_per_minute_components
        +
expected_win_bonus
        =
expected_fantasy_points
```

Where the actual implementation accounts for nonlinear or discrete components as necessary.

The model should be able to produce both:

```text expected_PIR
expected_fantasy_points
```

---

# 9. Head Coach architecture

Coach prediction remains separate from player prediction.

Inputs:

```text
expected_margin
margin uncertainty
home/away
team strength
opponent strength
```

Output:

```text probability of each scoring bracket
```

Then:

```text E[coach_points]
```

is computed from the exact fantasy scoring brackets.

Do not regress coach fantasy points as if they were continuous player scores.

The discrete bracket structure is a real property of the rules.

---

# 10. Uncertainty model

V0.2 currently uses a heuristic:

```text sigma = max(4, 0.45 * xPDK)
```

V0.3 should replace this with empirical uncertainty.

Candidate approaches:

### A. Historical residual variance

```text residual = actual - prediction
sigma = std(residual)
```

conditioned on:

```text player role
minutes
prediction level
```

### B. Quantile regression

Predict:

```text P10
P25
P50
P75
P90
```

This may eventually be preferable to assuming Gaussian outcomes.

### C. Empirical residual distribution

Store residual distributions by player/role and sample from them.

V0.3 should begin with the simplest method that survives evaluation.

---

# 11. Model candidates

Do not assume a single algorithm.

Evaluate:

```text Ridge
Elastic Net
Random Forest
Gradient Boosting
HistGradientBoosting
XGBoost/LightGBM if introduced as an optional dependency
```

The project should not require a heavy ML framework simply to run the deterministic manager.

A useful architecture is:

```text core runtime:
stdlib + sqlite

optional analytics:
numpy/pandas/sklearn
```

if dependency policy permits.

# 12. Feature groups

Organize features rather than maintaining a flat unstructured list.

## Player form

```text season average
last 3
last 5
last 10
EWMA
trend
variance
```

## Minutes/role

```text recent minutes
starter rate
minutes trend
DNP rate
rotation depth
```

## Production

```text points/min
rebounds/min
assists/min
stocks/min
FD/min
turnovers/min
```

## Team

```text team strength
team recent form
home/away
expected margin
```

## Opponent

```text opponent strength
position-specific FDR
opponent recent defensive performance
```

## Schedule

```text rest days
double-week
games in previous N days
games in next N days
```

## Market

```text current quotation
quotation change
```

Market features must remain explicitly identified as market-derived information.

# 14. Valuation layer

Do not mix valuation into performance prediction.

The valuation layer receives:

```text expected fantasy points
current quotation
expected minutes
uncertainty
future fixtures
```

and calculates:

```text points per credit
expected value
risk-adjusted value
```

This allows us to answer separately:

> How good is the player?

and:

> How good is the player at this price?

---

# 15. Capital Gain model

Capital gain is a separate prediction target.

Potential target:

```text future_quotation - current_quotation
```

or, preferably, a defined post-round quotation change.

Features:

```text current quotation
recent fantasy performance
xPDK
popularity/ownership if available
market trend
player availability
```

The first version should be evaluated against simple price-change baselines.

Do not assume that xPDK automatically predicts price changes.

---

# 16. Optimizer integration

The optimizer should consume a generic prediction object.

For example:

```python
PlayerProjection(
    player_id,
    expected_points,
    uncertainty,
    play_probability,
    expected_minutes,
    quotation,
)
```

The optimizer should not know whether the projection came from:

```text V0.2 heuristic
V0.3 Ridge
V0.3 Gradient Boosting
future neural network
```

This creates a clean model/optimizer boundary.

---

# 17. Risk profiles

Risk profiles should modify the optimization objective, not the prediction itself.

For example:

```text neutral:
maximize E(score)

floor:
maximize lower percentile

ceiling:
maximize upper percentile

defend_lead:
penalize variance

chase:
reward upside
```

Do not create separate prediction models for each risk profile unless evaluation later proves it necessary.

---

# 18. Backtesting architecture

Every model must be evaluated through the same interface:

```python
model.fit(history)
prediction = model.predict(cutoff_data)
```

The evaluator controls:

```text training cutoff
test period
feature construction
target construction
metrics
```

This prevents individual models from implementing their own incompatible backtest logic.

---

# 19. Model registry

Introduce a simple registry:

```text
xpdk_v02
season_mean
last5
ewma
xpdk_v03_ridge
xpdk_v03_gbm
```

Each model should declare:

```text name
version
required_features
training window
hyperparameters
```

This makes experiments reproducible.

# 20. V0.3 acceptance criteria

V0.3 should not be declared complete merely because a component model exists.

It must satisfy:

### Prediction
- [ ] Expected minutes model exists and is evaluated.
- [ ] Availability model exists or a justified baseline is retained.
- [ ] Component projections exist.
- [ ] Expected fantasy points are reconstructed deterministically.
- [ ] Empirical uncertainty is evaluated.

### Evaluation
- [ ] Walk-forward backtesting is automated.
- [ ] V0.3 is compared against V0.2.
- [ ] Simple baselines remain in every comparison.
- [ ] No leakage tests fail.

### Decision quality
- [ ] Model ranking improves or is demonstrably competitive.
- [ ] Lineup simulations are evaluated.
- [ ] Captain/bench decisions can be measured.
- [ ] The model does not merely improve MAE while producing worse fantasy decisions.

### Engineering
- [ ] Prediction objects are model-agnostic.
- [ ] Model version is persisted.
- [ ] Historical predictions can be reproduced.
- [ ] Core manager remains usable without optional ML dependencies.

---

# 21. What V0.3 deliberately does not solve

Defer:

- exact multi-round optimization;
- full transfer planning;
- live T1 -> T2 optimizer;
- ownership strategy;
- LLM;
- GUI;
- EuroCup;
- deep injury/news NLP.

Those should consume the V0.3 projection layer later.

# 22. Expected evolution after V0.3

```text
V0.2
heuristic xPDK
    ↓
V0.25
prove what works
    ↓
V0.3
validated predictive projections
    ↓
V0.35/V0.4
multi-round + transfer optimization
    ↓
V0.4+
exact live Turn decisions
    ↓
V0.5
GUI / multi-team
    ↓
V0.6+
LLM strategic layer + historical decision backtesting
```

The important invariant is:

```text
Prediction
    ≠
Valuation
    ≠
Optimization
    ≠
LLM advice
```

Each layer has one responsibility.
