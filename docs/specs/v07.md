# V0.7 — Full Trade Capacity, Historical Round Backfill & Sequential Decision Replay

> **Status:** Planned — active on branch `v07` (created from `main` after PR #11 merged V0.6.5).
> **Planning baseline:** 2026-09-30
> **Objective:** Close five concrete correctness/usability gaps found in day-to-day V0.6.5 use, and deliver the
> sequential historical decision replay and multi-season backtesting capability already scheduled for V0.7 in
> [`../roadmap.md`](../roadmap.md).
> **Rule:** V0.7 introduces **no new prediction model**. It raises the decision engine to its full legal
> action space (4 trades), makes the full player universe reachable, brings the LLM provider surface to parity
> with `fpl-manager` v0.6+, and adds historical state reconstruction plus replay evaluation.

---

## 1. Why V0.7 exists

V0.6.5 hardened the stack, but live usage surfaced five issues that are *not* model problems — they are
**artificially narrowed interfaces**. In each case the engine or the storage layer is already capable, and a
default value, a hardcoded GUI constant or a missing parameter is throttling it:

| # | Observed symptom | Actual cause | Engine already capable? |
|---|---|---|---|
| 1 | Only ever 2 trades proposed | GUI hardcodes `Math.min(2, …)`; API/service defaults are `1` | **Yes** — `k = 1..4` already implemented and tested |
| 2 | Suggester feared too slow past 2 trades | Assumption, not measurement; pruning already scales with `k` | **Yes** — Stage-2 cost is constant in `k` |
| 3 | Cheapest players missing from manual transfers | Endpoint sorts by value then truncates (`[:limit]`) | **Yes** — full universe is loaded, then discarded |
| 4 | Cannot enter an OpenRouter key or pick a sub-model | GUI never renders a key field nor sends `api_key`/`model` | **Yes** — request model already accepts both |
| 5 | Cannot record a past round | Write endpoints have no `round_number` parameter | **Partly** — storage is already keyed per round |

The sixth workstream is the roadmap's original V0.7 content. It depends on W5, because replaying history
requires the ability to *represent* a historical round in the first place.

## 2. Principles

1. **The engine may use its full legal action space.** The EuroLeague ruleset grants **4** trades per round
   (`rules.py::MAX_TRADES_PER_ROUND = 4`). No layer above the engine may silently narrow that. Any cap must be
   derived from the team's actual `transfers_remaining`, never hardcoded.
2. **Truncation is a display concern, never an existence concern.** A list endpoint may paginate, but it must
   never make a legal choice *unreachable*. If a response is truncated, it must report the total and offer an
   offset.
3. **Secrets never appear in an error path.** Once a user-supplied API key can reach the process, every
   exception message, log line and HTTP detail that could embed it must be redacted.
4. **Backfill is explicit and auditable.** Writing a past round is only ever possible through an explicit
   write endpoint/CLI command carrying an explicit round. Advisory read paths keep the V0.6 zero-mutation
   invariant unchanged.
5. **History is reconstructed, not mutated.** Replay reads point-in-time state; it never rewrites the stored
   squad history to make a model look better.

## 3. W1 — Full trade capacity (4 per round)

**Problem.** `optimization/transfers.py` already enumerates `k = 1..4` and clamps at 4, and
`test_v04_optimization.py::test_transfer_trade_counts_1_to_4_and_unlimited` already proves it works. Every
*caller* understates it.

**Changes.**

| File | Current | Target |
|---|---|---|
| `web/static/js/app.js:1279` | `Math.min(2, tradeStudioState.transfersRemaining \|\| 1)` | derive from `transfersRemaining`, cap at `MAX_TRADES_PER_ROUND` |
| `web/api/routes_workstation.py:51` | `max_trades: int = 1` | `= 4` |
| `services/optimization_service.py:251` | `max_trades: int = 1` | `= 4` |
| `optimization/multi_round.py:53` | `max_trades_per_round: int = 2` | `= 4` |
| `cli.py:496` | `--max-trades` default `2` | `4` |
| `intelligence/dossier.py:395` | `min(team.transfers_remaining, 3)` | `min(team.transfers_remaining, MAX_TRADES_PER_ROUND)` |
| `docs/roadmap.md:386,411` | "the 3 free trades" | "the 4 free trades" |

**Acceptance criteria.**
- A1. With a team holding 4 `transfers_remaining`, the Trade Studio POST body carries `max_trades: 4`.
- A2. The suggester returns ranked packages of `trade_count` 1, 2, 3 **and** 4, and a 4-trade package is only
  recommended when it beats every smaller package net of its cost.
- A3. No magic number `2` or `3` remains as a trade cap anywhere outside `rules.py`.
- A4. A team with fewer remaining trades is still correctly limited to that number.

## 4. W2 — Suggester performance validation at k=4

**Problem.** The concern is real in principle — `C(15,4) = 1365` out-combinations — but the existing design
already anticipates it. Measured before tuned.

**Existing mitigations** (`optimization/transfers.py`):
- per-`k` candidate pool shrinkage: `cand_limits = {1: 15, 2: 8, 3: 5, 4: 4, 5: 3}`
- budget feasibility pruning before evaluation
- a `2.0x / 0.5x` expected-points upper-bound prune
- **Stage-2 top-25 cutoff** — only 25 packages ever reach the expensive lineup solve, so the costly phase is
  **O(1) in k**.

**Changes.**
- B1. Benchmark `optimize_transfers` at `k = 1..4` against a realistic market (≥200 players) and record results.
- B2. Only if a measured budget is exceeded: tune `cand_limits`, or make the Stage-2 cutoff adaptive.
- B3. Extend the perf regression test (`test_v05_multi_team_and_gui.py:1650`) from `(1, 2, 3)` to `(1, 2, 3, 4)`.

**Acceptance criteria.**
- B4. `k=4` completes within the documented per-call budget on the reference market.
- B5. Results remain deterministic: identical inputs produce an identical ranked package list.

## 5. W3 — Reachable player universe for manual transfers

**Problem.** `web/api/routes_workstation.py:697-698`:

```python
filtered.sort(key=lambda x: -x["expected_fp"])
return filtered[:limit]
```

Sorting by value and *then* truncating means the cheapest players can never be returned, whatever the caller
does — and `app.js:1396` requests only `limit=40`. There is no `offset`, so there is no "rest of the list".

**Changes.**
- C1. Add `offset: int = 0` and return a structured payload carrying `total`, `offset`, `limit` alongside `items`.
- C2. Add an explicit `sort` parameter (`expected_fp` | `price` | `name`), keeping `expected_fp` as default so
  existing callers are unaffected in ordering.
- C3. Keep server-side `search`, `position`, `min_price`, `max_price` filtering — these are user-driven and legitimate.
- C4. GUI: drop the hardcoded `limit=40`; drive the picker from search-as-you-type against the `search`
  parameter, and allow paging when no search term is present.

**Acceptance criteria.**
- C5. The cheapest player in the market is reachable in the manual-transfer picker, via search and via paging.
- C6. `total` reflects the count *after* filtering and *before* truncation.
- C7. Backwards compatibility: existing callers that pass only `limit` still work.

## 6. W4 — LLM provider parity with `fpl-manager` v0.6+

**Problem.** The backend is in good shape — it already implements Heuristic, Gemini, OpenAI, Claude,
OpenRouter and Local providers, already exposes `GET /api/workstation/copilot/providers`, and
`CopilotAdviseRequest` **already accepts `api_key` and `model`**. The GUI simply never offers them: there is no
key input, no sub-model selector, and `triggerCopilotAdvise()` omits both fields from its payload.

**Target model, following `fpl-manager`:** OpenAI and Gemini are paid providers keyed by the user; OpenRouter
takes a GUI-entered key and exposes selectable sub-models, mostly free, with paid ones marked `*`.

**Changes.**
- D1. Extend `intelligence/providers.py::list_available_providers()` so each provider carries a
  `models: [{id, name, free}]` catalog. This is **server-driven**, improving on `fpl-manager`'s
  client-hardcoded table, and must also cover Claude and Local (which have no `fpl-manager` equivalent).
- D2. GUI: add a password-type API key input with a show/hide toggle, persisted per provider in `localStorage`
  (`elf_copilot_api_key_<provider>`), mirroring `fpl-manager`'s per-provider convention.
- D3. GUI: add a sub-model `<select>` populated from the provider catalog, rendering a trailing `*` and a
  tooltip for paid models.
- D4. Wire `api_key` and `model` into the `triggerCopilotAdvise()` payload.
- D5. **New** `intelligence/security.py` with `redact_secrets()`, applied in every provider exception handler
  and in `routes_intelligence.py` HTTP error details. `fpl-manager` has this; this repo does not, and W4 is
  what makes it necessary.
- D6. Add an `"auto"` provider mode selecting the first provider with a configured key.

**Acceptance criteria.**
- D7. A user can paste an OpenRouter key in the GUI, pick a free sub-model, and receive advice — with no
  environment variable set.
- D8. The key is never written to the database, never logged, and never echoed in an error response.
- D9. Selecting a paid sub-model shows the `*` marker and an explanatory tooltip.
- D10. With no key configured anywhere, the Copilot still falls back to the deterministic heuristic provider.

## 7. W5 — Historical round backfill

**Problem.** Storage is *already* per-round: `managed_team_squads` is keyed
`PRIMARY KEY (team_id, round_number, player_id)` and `team_round_checkpoints` supports
`get_checkpoint_at_or_before()`. `GET /api/workstation/dashboard` already accepts an optional `round_number`.
What is missing is (a) any GUI affordance to choose a round and (b) a `round_number` on the **write** path —
`UpdateLineupRequest` and `ExecuteTransfersRequest` both implicitly target `team.round_number`.

**Changes.**
- E1. Add `round_number: int | None = None` to `UpdateLineupRequest` and `ExecuteTransfersRequest`, threading it
  through `TeamService.update_lineup` / `execute_transfers`. `None` preserves today's "current round" behaviour.
- E2. Add a `team_transfers` event table (`team_id, round_number, season, player_out_id, player_in_id,
  price_out_tenths, price_in_tenths, created_at`). Today only the *resulting squad* is stored, so the trade
  events themselves are unrecoverable — W6 needs them. Follow the existing ad-hoc
  `PRAGMA table_info` + `ALTER TABLE` migration pattern (`multi_team/store.py:90-96`); there is no migration framework.
- E3. Recompute downstream `team_round_checkpoints` when a past round is edited. Checkpoints are currently only
  ever written forward, and `get_checkpoint_at_or_before()` assumes chronological consistency — editing round *n*
  invalidates every checkpoint after it.
- E4. GUI: add a round selector to the Lineup tab, introducing `state.viewRoundNumber` distinct from the team's
  live `state.roundNumber`, and pass it to the dashboard endpoint (already supported).
- E5. Add a `GET /api/teams/{team_id}/rounds` endpoint enumerating rounds that have stored state.
- E6. CLI: accept `--round` on the lineup and transfer entry commands.

**Acceptance criteria.**
- E7. A lineup and a set of trades can be recorded for a past round and read back unchanged.
- E8. Editing round *n* leaves rounds `< n` untouched and produces consistent bank/transfer state for rounds `> n`.
- E9. The V0.6 zero-mutation invariant test
  (`test_v06_strategic_intelligence.py::test_strong_zero_mutation_invariant`) still passes — advisory paths
  remain read-only; only explicit write endpoints mutate.
- E10. Omitting `round_number` behaves exactly as V0.6.5 did.

## 8. W6 — Sequential historical replay & multi-season backtesting

This is the roadmap's original V0.7 scope, unlocked by W5's point-in-time representation.

- F1. **Multi-season historical datasets** — ingest historical round snapshots for EuroLeague and EuroCup
  across 2022-23 … 2025-26.
- F2. **Point-in-time state reconstruction** — rebuild squad valuation, bank, availability and price changes at
  every historical round boundary, reusing W5's per-round storage.
- F3. **Sequential decision simulation** — simulate lineup, captaincy, sixth man, T1→T2 turn substitution and
  transfer decisions across whole seasons.
- F4. **Model-version comparison ledgers** — standardized ledgers comparing decision versions against actual
  human decisions and a hindsight oracle.
- F5. **Historical regret attribution** — decompose season regret into Captain, Sixth Man, Bench, Turn
  Substitution and Transfer regret.

**Acceptance criteria.**
- F6. A full season replays deterministically end-to-end with no network access in tests.
- F7. Regret components sum to total measured regret within a documented tolerance.
- F8. Replay is strictly read-only with respect to live team state.
