# V1.0 — Mature Multi-League Fantasy Decision Platform

> **Status:** Long-term target  
> **Definition:** Complete enough to use, correct enough to trust, reproducible enough to research, observable enough to evaluate, modular enough to extend.

## 1. V1.0 Is a Maturity Milestone

V1.0 is not "the system has every possible feature."

It means the architecture and workflow are coherent enough that a technically competent human can understand and audit the complete decision chain.

The system is not an oracle and is not autonomous.

## 2. Target Architecture

```text
Official data
     ↓
Point-in-time snapshots
     ↓
League-aware deterministic rules
     ↓
Prediction
     ↓
Valuation
     ↓
Optimization
     ↓
Decision log
     ↓
Actual outcome
     ↓
Evaluation / replay
     ↓
Manager Dossier
     ↓
Deterministic strategic analysis
     ↓
Optional LLM interpretation
     ↓
Human decision
```

Higher-level interpretation must never silently override lower-level deterministic truth.

## 3. Multi-League Foundation

V1.0 supports:

- EuroLeague
- EuroCup

through a shared engine.

### Shared components

- data contracts
- persistence
- team model
- prediction contracts
- valuation contracts
- optimization contracts
- decision logging
- evaluation/backtesting
- services
- CLI
- workstation

### Competition-specific components

Explicit adapters/rulesets provide:

- scoring rules
- roster/formation rules
- position terminology
- competition metadata
- other documented competition-specific constraints

There must not be separate application forks for EuroLeague and EuroCup.

## 4. Team Architecture

A single team model carries competition metadata.

```text
Team
 ├── identity
 ├── league
 ├── squad
 ├── bank
 ├── transfer state
 ├── checkpoints
 ├── decisions
 ├── scenarios
 └── provenance
```

The workstation supports up to **6 isolated teams per user**.

Teams can belong to different competitions.

Required property:

> No team can accidentally read or mutate another team's persistent fantasy state.

## 5. Prediction Quality

The prediction layer must provide:

- point-in-time correctness
- explicit feature cutoffs
- availability / play probability
- expected minutes
- production per minute
- calibrated uncertainty where supported
- cold-start handling
- leakage tests
- model/version provenance
- reproducible evaluation

The decomposition remains conceptually:

```text
E[FP] =
P(play)
× E(minutes | play)
× E[FP/min | play)
× context factors
```

The exact implementation may evolve, but the provenance and evaluation boundaries must remain explicit.

## 6. Decision Engine

The deterministic optimizer must support the mature workflows established through V0.4–V0.5:

- initial team construction
- lineup optimization
- captain selection
- sixth-man selection
- bench selection
- transfers
- unlimited transfer windows
- T1/T2/T3 intra-round decisions
- multi-round planning
- configurable risk assumptions

Exact and heuristic components must be clearly documented.

No heuristic result should be presented as globally optimal unless its scope of optimality is established.

## 7. Closed-Loop Evaluation

The platform must preserve the distinction between:

```text
prediction
   ↓
recommendation
   ↓
human decision
   ↓
actual outcome
```

It should support:

- prediction error
- decision regret
- recommendation-vs-human comparison
- historical replay
- model-version comparison
- sequential backtesting
- point-in-time reconstruction

Historical analysis must not leak future information into the simulated decision state.

## 8. Manager Dossier

The Manager Dossier is the stable boundary between the deterministic engine and strategic interpretation.

It includes:

- team/league state
- projections
- uncertainty
- valuations
- optimizer recommendations
- alternatives
- transfer packages
- intra-round options
- multi-round candidates
- schedule/context
- provenance

The dossier schema is competition-agnostic.

## 9. Strategic Intelligence

The strategic layer has two levels.

### Deterministic

- assumption breakdown
- sensitivity analysis
- rule checks
- forecast checks
- alternative checks
- regret checks
- context/change checks

### Optional LLM

- briefing
- explanation
- challenge
- alternative comparison
- uncertainty interpretation
- scenario analysis
- change detection

The LLM is advisory.

It cannot:

- execute transfers
- mutate team state silently
- override rules
- replace optimizer calculations
- invent numerical facts

## 10. Reproducibility

A decision should be reproducible from recorded:

- data snapshot
- league
- ruleset version
- model version
- feature cutoff
- prediction configuration
- optimizer configuration
- risk mode
- team state
- dossier version
- prompt/model provenance when LLM is used

Secrets must never be included in provenance.

## 11. Reliability

The system should fail safely.

Examples:

- data provider failure → explicit error, no corrupted state
- LLM provider failure → deterministic dossier/analysis remains usable
- invalid rules configuration → fail fast
- inconsistent checkpoint → reject rather than silently repair
- cross-team access → blocked/tested
- malformed model output → validation failure, not state mutation

## 12. Testing

V1.0 requires layered testing:

### Unit tests
Rules, models, adapters, calculations.

### Contract tests
Service/API/storage interfaces.

### Regression tests
All previous release functionality.

### Leakage tests
Future information cannot affect historical reconstruction.

### Optimization correctness tests
Exact algorithms compared against brute-force/reference solutions where feasible.

### Multi-league tests
Equivalent workflows exercised across EuroLeague and EuroCup with their respective rulesets.

### Multi-team isolation tests
Six-team scenarios with mixed competitions.

### AI consistency tests
LLM output checked against dossier facts and rules.

## 13. Observability & Auditability

For each meaningful decision, the system should make it possible to inspect:

1. state at decision time
2. available information
3. predictions
4. assumptions
5. optimizer configuration
6. recommendations
7. alternatives
8. human decision
9. actual outcome
10. evaluation

The goal is an auditable decision history rather than a black-box recommendation log.

## 14. Explicit Non-Goals

V1.0 does not require:

- autonomous management
- automatic transfers
- cloud SaaS
- mobile applications
- perfect prediction
- perfect historical reconstruction
- universal strategy
- guaranteed fantasy performance
- LLM autonomy
- replacing deterministic rules with AI

## 15. V1.0 Acceptance Questions

A technically competent human should be able to answer:

### Data
What information was available at the time?

### Rules
Which competition rules were active?

### Prediction
What did the system predict and with what model/version?

### Optimization
Why was this legal decision recommended?

### Alternatives
What other deterministic choices were available?

### Strategy
Which assumptions and sensitivities mattered?

### Human
What did the manager actually choose?

### Outcome
What happened?

### Evaluation
How much error/regret resulted?

### Reproducibility
Can the decision be recreated from the recorded state?

If the system can answer these questions reliably, V1.0 has achieved its intended maturity bar.

> **V1.0 is a trustworthy decision platform, not an oracle.**
