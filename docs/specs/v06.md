# V0.6 — Strategic Intelligence, Manager Dossier & Multi-League Foundation

> **Status:** Implemented (V0.6)  
> **Objective:** Add strategic interpretation around the deterministic engine while establishing the shared multi-league architecture.  
> **Architecture:** Common engine → league adapter → Manager Dossier → deterministic analysis → optional LLM → human decision.  
> **Compatibility Boundary:** V0.6 establishes EuroCup architectural compatibility; full EuroCup feature/rule parity remains a V0.9 objective.

## 1. Core Principle

> **V0.6 adds intelligence around the engine, not intelligence instead of the engine.**

The deterministic stack remains authoritative.

The LLM may explain, challenge, compare and interpret. It must not silently change rules, predictions, scores, legality or persistent team state.

The architecture must support EuroLeague and EuroCup through the same engine, contracts, APIs and storage patterns. Competition-specific behavior belongs in explicit league/rules adapters, not forks of the application.

```text
official data
      ↓
common data/state layer
      ↓
league-aware rules/state
      ↓
common prediction contracts
      ↓
common valuation / optimization contracts
      ↓
Manager Dossier
      ↓
deterministic strategic analysis
      ↓
optional LLM Copilot
      ↓
human decision
      ↓
decision log
```

## 2. Multi-League Architecture

V0.6 establishes league awareness as a first-class architectural concern.

### 2.1 Shared engine

The following remain common across competitions:

- API/service contracts
- storage schema and persistence patterns
- team model
- prediction interfaces
- valuation interfaces
- optimization interfaces
- decision logging
- provenance
- evaluation infrastructure
- CLI/service architecture
- GUI/workstation architecture

### 2.2 League adapter

Competition-specific behavior is supplied through explicit adapters/rulesets:

```text
Shared Rules Engine Contract
        │
        ├── EuroLeague Ruleset
        └── EuroCup Ruleset
```

The goal is **one rules-engine contract with league-specific rulesets**, not one universal hard-coded ruleset.

Position names, role abbreviations, roster constraints, formations, salary/cap rules and scoring differences must be resolved through the active league configuration.

### 2.3 Team model

A team carries its competition metadata:

```python
Team(
    team_id=...,
    league=League.EUROLEAGUE,
    ...
)
```

Do not create separate application-level `EuroLeagueTeam` and `EuroCupTeam` models.

The same team/service/storage primitives must work for either league.

### 2.4 Six-team capacity

The workstation/team model must support up to **6 isolated teams per user**.

Each team has:

- unique team identity
- league metadata
- independent squad
- independent bank/transfers/state
- independent decision history
- independent scenarios/checkpoints
- independent provenance

Shared engine components must remain stateless with respect to a particular team unless explicit team state is passed to them.

## 3. Manager Dossier

Create a deterministic, structured dossier containing:

- **Team/Squad/Bank/Round/Turn State:** squad units, bank credits, transfers remaining, league, round and turn
- **Projections:** expected fantasy points, expected minutes, play probability, FP/min, uncertainty bands
- **Valuations:** price, value, PAR and efficiency metrics
- **Optimizer Recommendations:** lineup recommendation, legal alternatives and risk modes
- **Transfer Packages:** multi-option recommendations ranked by the configured deterministic objective
- **Intra-Round Alternatives:** T1 → T2 → T3 substitution/captain options with projected gains
- **Multi-Round Candidates:** forward-looking squad plans
- **Relevant Schedule/Context:** fixtures, available team/context data and opponent information
- **Prediction and Optimizer Provenance:** model versions, cutoff timestamps and configuration snapshots

Every quantitative fact must remain traceable to its source/run/cutoff where practical.

### Multi-League Dossier Contract

The dossier schema is competition-agnostic.

Competition-specific presentation metadata may include:

- position labels
- role abbreviations
- formation terminology
- ruleset identifiers

The underlying dossier structure remains identical.

## 4. Deterministic Strategic Analysis

Before invoking an LLM, generate deterministic strategic signals.

### Assumption Breakdown

Identify the top 3–5 assumptions by estimated decision impact, such as:

- participation probability
- expected minutes
- efficiency
- location multiplier
- schedule/context assumptions

### Sensitivity Analysis

Perform one-way perturbations of important assumptions and show whether the recommendation changes.

### Devil's Advocate Checklist

At minimum:

- **Rule Check:** Is the recommendation legal?
- **Forecast Check:** Are the projections plausible relative to the dossier?
- **Alternative Check:** Is an important deterministic alternative missing?
- **Regret Check:** What is the downside if the key assumption fails?
- **Context Check:** What changed since the previous decision?

This layer must work fully with the LLM disabled.

## 5. LLM Copilot

The optional LLM layer mirrors the mature patterns established in `fpl-manager`.

It may provide:

- **Manager Briefing:** concise summary of current state and recommendation
- **Optimizer Explanation:** why a lineup, captain or transfer package was selected
- **Alternative Comparison:** comparison of top deterministic alternatives
- **Devil's-Advocate Critique:** challenge assumptions and identify risks
- **Risk/Uncertainty Interpretation:** explain uncertainty and edge cases
- **Scenario Comparison:** e.g. trade now vs wait for next round
- **Change Detection:** summarize meaningful changes since the previous decision

The LLM receives a structured dossier and deterministic analysis. It does not become a source of raw fantasy truth.

## 6. Provider Architecture

Mirror the provider abstraction used by `fpl-manager`.

Target interface:

```text
Copilot
  └── Provider interface
       ├── OpenAI
       ├── Claude
       ├── OpenRouter
       └── Local
```

Provider implementations must be replaceable without changing the deterministic engine.

### Tiers

Support configurable analysis tiers such as:

- **fast:** low latency / local or lightweight model
- **standard:** normal API analysis
- **extended:** slower/deeper reasoning

V0.6 does not require multi-provider orchestration or automatic routing.

### Failure behavior

If the provider fails:

```text
LLM failure
   ↓
deterministic dossier remains valid
   ↓
deterministic strategic checklist remains available
   ↓
team state remains unchanged
```

No provider failure may corrupt or partially mutate persistent team state.

## 7. Human Control

V0.6 must not:

- execute transfers automatically
- mutate team state without confirmation
- override official rules
- replace optimizer calculations
- invent numerical facts
- silently rewrite deterministic recommendations

Workflow:

```text
engine → dossier → analysis → human → confirmed decision
```

The human remains responsible for the final decision.

## 8. Provenance

Record, where applicable:

- LLM provider
- model name/version
- prompt version
- prompt content hash
- dossier version
- dossier generation timestamp
- configuration snapshot
- league
- team
- risk mode
- transfer budget
- analysis tier
- analysis timestamp

Never store API keys, secrets or credentials in provenance records.

## 9. Numerical and Rule Consistency

LLM output must be treated as an interpretation of the dossier.

Implement checks so that:

- numerical claims can be traced to dossier values
- player names/identifiers correspond to dossier entities
- recommendation descriptions correspond to actual optimizer outputs
- stated alternatives exist in the deterministic result set
- rules referenced by the LLM correspond to the active league ruleset
- contradictions can be flagged before presentation where practical

The LLM must never be trusted to independently reconstruct fantasy rules.

## 10. Evaluation

Evaluate the copilot itself rather than claiming that prose quality automatically improves fantasy performance.

Metrics include:

- factual consistency
- rule consistency
- numerical consistency
- alternative representation accuracy
- contradiction rate
- provenance completeness
- deterministic fallback availability
- latency
- human usefulness feedback

Do not claim fantasy-performance improvement merely because users prefer the narrative.

## 11. Tests

Required tests include:

- dossier generation deterministic and reproducible
- provenance complete
- provenance immutable after creation
- LLM-disabled path works
- provider failure cannot corrupt team state
- LLM cannot mutate persistent state directly
- numerical claims can be checked against dossier
- prompt/model provenance recorded
- EuroLeague and EuroCup dossier compatibility
- league metadata survives persistence round-trip
- league-specific ruleset is selected dynamically
- deterministic strategic checklist works without LLM
- six-team isolation
- no cross-team state leakage
- copilot latency benchmark on realistic dossiers
- existing V0.1–V0.5.1 regression suite remains green

## 12. Out of Scope

- autonomous management
- automatic transfer application
- new prediction models
- new optimizer algorithms
- full historical sequential replay (V0.7)
- complete EuroCup feature parity (V0.9)
- multi-provider orchestration/routing
- LLM-controlled team state
- replacing deterministic evaluation with LLM judgement

## 14. Alignment with FPL Manager

V0.6 deliberately mirrors the proven LLM/dossier architecture from `fpl-manager`:

- provider abstraction
- prompt versioning
- structured manager dossier
- OpenRouter support where appropriate
- graceful fallback
- error isolation
- numerical consistency checks
- explicit provenance
- disciplined evaluation
- documented test dispositions

The implementation should reuse the **architectural pattern**, not blindly copy competition-specific rules or assumptions.

## 15. Definition of Done

A user can:

1. Select any of up to 6 isolated teams.
2. Each team carries explicit EuroLeague/EuroCup metadata.
3. Generate a deterministic Manager Dossier.
4. Inspect recommendations and alternatives.
5. Run deterministic strategic analysis without an LLM.
6. Optionally request LLM explanation, challenge or scenario analysis.
7. Trace quantitative claims back to deterministic evidence.
8. Survive provider failures without state corruption.
9. Make the final human decision.
10. Log that decision with full provenance.

> **V0.6 establishes the shared multi-league intelligence architecture while keeping the deterministic engine authoritative.**
