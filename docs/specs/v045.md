# V0.45 — Closed-Loop Evaluation & Live Decision State

> **Status:** Completed (`0.4.5`, 2026-09-23)  
> **Prerequisite:** V0.4 deterministic decision and optimization layer.
>
> **Primary objective:** Connect the quantitative engine to real management decisions and actual outcomes, creating the first closed loop between **prediction → decision → reality → evaluation → improvement**.
>
> **Core principle:** V0.45 is deliberately not a new prediction or GUI release. It is the bridge that makes the existing V0.3/V0.4 system measurable when used as an actual fantasy manager.

---

# 1. Why V0.45 exists

V0.3 established:

```text
validated predictions
```

V0.4 established:

```text
decisions and optimization
```

But there is still a missing link:

```text
prediction
    ↓
optimization
    ↓
WHAT DID WE ACTUALLY DO?
    ↓
WHAT ACTUALLY HAPPENED?
    ↓
HOW GOOD WAS THAT DECISION?
```

V0.45 closes this loop.

The resulting system becomes:

```text
point-in-time data
      ↓
V0.3 prediction
      ↓
V0.4 optimization
      ↓
human decision
      ↓
decision log
      ↓
actual fantasy outcome
      ↓
regret / prediction error
      ↓
model + strategy diagnostics
```

This foundation is required before V0.5 turns the system into a multi-team GUI.

---

# 2. V0.45 success criteria

V0.45 is complete when:

- [x] A fantasy decision can be recorded with complete provenance.
- [x] The decision can be retrieved later.
- [x] Actual outcomes can be attached to the decision.
- [x] Prediction error can be calculated retrospectively.
- [x] Decision regret can be calculated retrospectively.
- [x] Turn 1 → Turn 2 decisions can be evaluated.
- [x] Captain decisions can be evaluated.
- [x] Sixth-man and bench decisions can be evaluated.
- [x] Lineup decisions can be evaluated.
- [x] Transfer decisions can be evaluated.
- [x] Model drift can be monitored over time.
- [x] Historical decision records remain immutable/auditable.
- [x] Multiple independent fantasy teams can be represented safely.
- [x] CLI workflows support the complete closed loop.
- [x] All evaluation uses the same deterministic fantasy scoring layer as V0.1–V0.4.
- [x] Generic `INITIAL_TEAM` decision support is established for V0.5 consumption.

---

# 3. What V0.45 is NOT

Do not turn V0.45 into:

- a new predictive model release;
- a GUI release;
- an LLM strategy release;
- a live scraping system;
- a cloud service;
- an autonomous fantasy-account manager;
- a complete historical season simulator.

Those belong elsewhere.

V0.45 is primarily a **data/state/evaluation bridge**.

# 4. Core data model

The central entity is a **Decision Record**.

Conceptually:

```python
DecisionRecord(
    decision_id,
    team_id,
    season,
    round,
    turn,
    decision_type,
    decision_timestamp,
    state_snapshot,
    selected_lineup,
    formation,
    captain,
    sixth_man,
    bench,
    coach,
    transfers,
    prediction_run_id,
    optimization_run_id,
    objective,
    risk_mode,
    option_value_mode,
    notes,
)
```

The exact implementation can evolve, but the record must answer:

> What did we know, what did the system recommend, what did the manager choose, and when?

---

# 5. Phase A — Decision logging

Add a deterministic CLI command:

```powershell
elf log-decision
```

It should support recording:

### Lineup decision

- starters;
- formation;
- captain;
- sixth man;
- bench;
- coach.

### Transfer decision

- players out;
- players in;
- number of transfers;
- budget before/after;
- resulting squad.

### Turn decision

- observed Turn 1 state;
- substitution;
- captain switch;
- resulting Turn 2 lineup.

The command should be able to record either:

```text
optimizer recommendation
```

or:

```text
human-selected alternative
```

because comparing the two is one of the main reasons V0.45 exists.

---

# 6. Phase B — Recommendation vs actual decision

Do not overwrite the optimizer recommendation when the human makes a different choice.

Store both:

```text
recommended_decision
actual_decision
```

This enables:

```text
model vs human
```

analysis.

For example:

```text
Optimizer:
    Captain = Player A

Human:
    Captain = Player B
```

Later:

```text
Actual A = 12
Actual B = 21
```

The system can calculate:

```text
human decision
vs
model recommendation
vs
oracle
```

without losing information.

---

# 7. Phase C — State snapshots

Every decision should preserve the relevant pre-decision state.

At minimum:

```text
season
round
turn
squad
prices
bank
available players
formation
current captain
current sixth man
transfers remaining
prediction run
optimizer run
```

The purpose is reproducibility.

A decision made on Round 4 should remain reconstructable even if the current database later changes.

Where practical, store:

```text
state_snapshot_id
dataset_version
```

rather than duplicating large raw datasets.

---

# 8. Phase D — Prediction provenance

Every recommendation must be traceable to the prediction that generated it.

Store:

```text
prediction_run_id
model_id
model_version
feature_version
dataset_version
prediction_cutoff
git_commit
parameter_signature
```

This allows later questions such as:

> Did the model change, or did the optimizer change?

and:

> Was the prediction generated using information available at the correct cutoff?

---

# 9. Phase E — Actual outcome ingestion

Add:

```powershell
elf update-scores
```

The command should attach actual results to previously logged decisions.

Possible sources:

- local historical data;
- current EuroLeague data;
- manually entered results where necessary.

The scoring pipeline must remain deterministic.

Do not let manually entered fantasy scores silently bypass the official scoring reconstruction.

---

# 10. Phase F — Prediction error

For every predicted player:

```text
prediction
actual fantasy points
```

calculate:

```text
error = actual - prediction
absolute_error = |actual - prediction|
```

Track:

- MAE;
- RMSE;
- bias;
- rank correlation where meaningful;
- calibration;
- availability error;
- minutes error;
- production error.

Because V0.3 is decomposed, V0.45 should eventually be able to identify where an error came from:

```text
availability error
        ↓
minutes error
        ↓
production error
        ↓
final FP error
```

This is one of the most valuable reasons for keeping the V0.3 decomposition architecture.

---

# 11. Phase G — Decision regret

For every actual decision:

```text
oracle score
-
actual decision score
=
decision regret
```

Track separately:

### Lineup regret

```text
oracle legal lineup
-
actual selected lineup
```

### Captain regret

```text
oracle captain contribution
-
actual captain contribution
```

### Sixth-man regret

```text
oracle sixth-man contribution
-
actual sixth-man contribution
```

### Bench regret

```text
oracle bench contribution
-
actual bench contribution
```

### Formation regret

Compare the actual formation against the best legal formation under realized outcomes.

---

# 12. Phase H — Model recommendation regret

Keep this distinct from human decision regret.

For every round:

```text
oracle
model recommendation
human decision
```

can produce:

```text
oracle regret
model regret
human regret
human-vs-model difference
```

Example:

```text
                 Actual Score
Oracle               231
Model recommendation 226
Human decision        221

Model regret            5
Human regret           10
Human vs model          -5
```

This is descriptive evaluation, not a rule that the model must always be followed.

---

# 13. Phase I — Turn 1 → Turn 2 evaluation

This is a central V0.45 feature.

For a Turn 1 decision:

```text
pre-T1 prediction
        ↓
T1 actual outcome
        ↓
manager decision
        ↓
T2 actual outcome
```

Record:

- original lineup;
- original captain;
- observed T1 results;
- available unplayed players;
- recommended substitution;
- actual substitution;
- recommended captain switch;
- actual captain switch;
- final result.

Then calculate:

```text
T2 decision regret
```

This should eventually allow evaluation of whether the V0.4 option-value machinery is useful in practice.

---

# 14. Phase J — Transfer evaluation

For each transfer decision:

```text
pre-transfer squad
transfer decision
post-transfer squad
```

track:

- immediate expected gain;
- realized gain;
- transfer cost/penalty if applicable;
- next-round score;
- future score;
- alternative transfer result;
- oracle alternative where reconstructable.

The first implementation can focus on:

```text
single-round transfer regret
```

before attempting sophisticated long-horizon attribution.

---

# 15. Phase K — Decision attribution

A useful V0.45 report should distinguish:

```text
prediction error
vs
optimization error
vs
human decision error
```

For example:

```text
Oracle:                 225
Optimizer recommendation: 220
Human decision:          214

Prediction/decision gap: 5
Human decision gap:      6
Total regret:           11
```

This prevents the project from incorrectly blaming the predictive model for a bad manual decision.

---

# 16. Phase L — Model drift monitoring

Track prediction performance over time.

Minimum rolling metrics:

- MAE;
- RMSE;
- bias;
- Spearman;
- Brier score;
- calibration;
- active-player MAE.

Potential windows:

```text
last 5 rounds
last 10 rounds
current season
historical baseline
```

The objective is not to automatically retrain.

The objective is to detect:

> “Is the model behaving differently from its historical validation?”

---

# 17. Phase M — Role/segment drift

Where sample size allows, monitor by:

- position;
- minutes bucket;
- starter/bench;
- availability state;
- team;
- player data richness;
- early/late season.

Examples:

```text
G MAE
F MAE
C MAE

starter MAE
bench MAE

data-rich MAE
cold-start MAE
```

Do not create dozens of metrics without sufficient data.

---

# 18. Phase N — Decision journal

Allow a lightweight human note:

```text
notes:
    "Kept Player A because expected T2 upside looked better."
```

This becomes useful later for V0.5 and the eventual LLM strategy layer.

Store notes as user input, not model truth.

Potential fields:

```text
decision_reason
confidence
manual_override
```

Do not force a structured explanation if the user does not want one.

# 21. Immutability and auditability

A logged decision should be treated as historical evidence.

Do not silently edit:

```text
what was recommended
what the user chose
what information was available
```

If a correction is necessary:

```text
original record
    ↓
correction event
```

rather than silently replacing history.

Actual outcomes can be updated when late data corrections occur, but the correction should remain auditable.

---

# 22. Point-in-time integrity

V0.45 must preserve the same rule as V0.2.5/V0.3:

> A decision may only depend on information available before that decision.

Therefore the stored state must preserve:

```text
decision cutoff
```

and:

```text
prediction cutoff
```

These may differ.

For Turn 2:

```text
T1 outcomes are now known
```

and therefore become valid inputs.

But Turn 2 cannot use:

```text
future T2 outcomes
```

or any later information.

---

# 24. V0.45 evaluation philosophy

The system should answer four separate questions:

### 1. Was the prediction good?

```text
actual vs predicted
```

### 2. Was the optimization good?

```text
recommended decision vs oracle
```

### 3. Was the human decision good?

```text
actual decision vs oracle
```

### 4. Did the human improve or worsen the model recommendation?

```text
human decision vs model recommendation
```

These are different questions and should remain different metrics.

# 25. Testing strategy

## Decision logging

- [ ] Round/turn state persists correctly.
- [ ] Team isolation works.
- [ ] Recommendation and human decision remain separate.
- [ ] Prediction/optimizer provenance persists.

## Point-in-time

- [ ] Future data cannot enter stored prediction state.
- [ ] T1 outcomes become available for T2 only.
- [ ] T2 outcomes cannot affect T1 records.

## Outcome updates

- [ ] Actual scores update correctly.
- [ ] Corrections are auditable.
- [ ] Fantasy scoring is deterministic.

## Regret

- [ ] Oracle score is correct.
- [ ] Model regret is correct.
- [ ] Human regret is correct.
- [ ] Human-vs-model comparison is correct.

## Replay

Given the same:

```text
state snapshot
prediction run
optimizer run
decision
```

the evaluation result should be reproducible.

# 32. Generic Extension for Initial-Team Creation Decisions (V0.5 Bridge)

To support future team-creation workflows without premature complexity, V0.45 includes a generic extension to its decision-record infrastructure:

### 1. Representability & Auditable Contract

* **Decision Type:** `DecisionType.INITIAL_TEAM = "initial_team"` is a first-class member of the `DecisionType` enum.
* **Separation of Recommendation vs. Human Decision:** `DecisionRecord` provides explicit fields `recommended_squad_ids: tuple[int, ...] | None` and `actual_squad_ids: tuple[int, ...] | None`.
* **State Snapshot Preservation:** An accompanying `StateSnapshot` captures the point-in-time player price quotations (`prices_tenths`), remaining budget (`bank_tenths`), and squad composition prior to Round 1 lock.
* **Provenance Tracking:** `DecisionProvenance` captures the algorithm lineage (`model_id`, `model_version`, `optimizer_version`, risk settings) of the initial team recommendation.
* **Override Detection:** `is_override` automatically detects differences between the recommended squad and the user-confirmed squad.

### 2. V0.5 Consumption Boundary

* **No GUI in V0.45:** V0.45 does not introduce GUI or web components for team drafting.
* **No Initial Team Optimizer in V0.45:** The combinatorial Initial Team Builder solver (e.g., full 11-player 100-credit portfolio optimizer) is deferred to V0.5.
* **V0.5 Initial Team Builder Consumer:** The eventual V0.5 Initial Team Builder will consume this capability directly via `DecisionLogger.log_initial_team_decision`, persisting both the optimizer's recommended squad and the manager's accepted or edited squad into SQLite with full provenance and auditability.
