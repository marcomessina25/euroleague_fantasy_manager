# V0.5 — Multi-Team Management & Local Web GUI

> **Status:** Completed (0.5.0, 2026-09-25)  
> **Prerequisites:** V0.4 (`0.4.0`) and 0.4.5 (`0.4.5`, completed on 2026-09-23) closed-loop decision/evaluation bridge.
>
> **Core principle:** The GUI is a downstream interface over the quantitative engine. It must not become a second rules engine, prediction engine, or optimizer.

## 1. Objective

Turn the CLI/research toolkit into a practical local fantasy-management workstation.

```text
data → rules/state → V0.3 predictions → V0.4 optimizer
     → V0.45 decision log/evaluation → V0.5 local GUI
     → human decision → actual outcome → evaluation
```

V0.3 predicts. V0.4 decides. V0.45 measures. V0.5 makes the whole workflow usable.

## 4. Phase A — Multi-team domain model

Each team should have:

```text
team_id
team_name
mode
squad
bank
round/turn state
settings
created_at
updated_at
```

Potential team preferences may include risk mode or optimization settings.

### Isolation
Team A must never read or mutate Team B/C:
- squad;
- bank;
- decisions;
- settings;
- scenarios.

Isolation belongs in the service/data layer, not only the UI.

## 7. Phase D — Half-court lineup view

Show:
- player;
- position;
- projected FP;
- captain;
- sixth man;
- turn;
- opponent;
- availability;
- uncertainty.

The frontend must not calculate these values.

## 8. Phase E — T1/T2/T3 state

Make turn state explicit:

```text
Turn 1 → current starters/captain
Turn 2 → remaining unplayed players + actions
Turn 3 → remaining decisions
```

The UI should expose the legal action space through V0.4 services.

## 9. Phase F — Turn substitution simulator

Workflow:

```text
current state
→ enter observed outcomes
→ recalculate
→ show best legal action
```

Show:
- realized score;
- replacement candidate;
- incremental gain;
- updated lineup;
- captain-switch value;
- uncertainty.

Clearly separate observed information from future prediction.

## 10. Phase G — Trade Studio

For candidate trades show:
- players out/in;
- price and bank impact;
- projected score change;
- value above replacement;
- risk change;
- future-round implications.

Filtering can include position, price, expected FP, value, availability, and club.

## 11. Phase H — Unlimited Trade Window

Provide a dedicated planning view:

```text
current squad → unlimited window → candidate squad → optimized lineup
```

Use the V0.4 rules/optimizer. Do not duplicate game rules in the GUI.

## 12. Phase I — Multi-round planner

Expose V0.4 beam-search plans:

```text
Round N   squad / action / projected score
Round N+1 squad / action / projected score
Round N+2 squad / action / projected score
```

Expose horizon, gamma, risk mode, cumulative score, and alternative paths.

Clearly label beam-search results as candidate paths, not guaranteed global optima.

## 13. Phase J — Evaluation hub

Show:

### Prediction

- bias;
- rank correlation;

### Decision
- lineup regret;
- captain regret;

## 14. Phase K — Decision comparison

Allow:

```text

vs

```

## 15. Phase L — Provenance

Every recommendation should expose:

```text

prediction run

```

This keeps recommendations auditable.

## 16. Phase M — What-if scenarios

Support disposable scenarios such as:

```text

Player B starts
transfer X made
conservative risk mode

```

Scenario state must not mutate persistent team state until explicitly saved.

## 17. Phase N — Application/service layer

Introduce explicit services such as:

```text
TeamService
PredictionService
OptimizationService
DecisionService
ScenarioService
EvaluationService
```

Example:

```python

    team_id=team_id,
    season=season,
    round=round,
    risk_mode="expected",
)
```

The GUI calls services, not database tables or internal optimizer classes directly.

## 29. Initial Team Builder Scope & Architecture

### Quantitative Architecture
- **Engine Placement**: Implemented in `euroleague_fantasy_manager.optimization.initial_team` using Exact Binary Integer Linear Programming (`scipy.optimize.milp`), with `OptimizationService` serving solely as an application adapter.
- **Constraints Enforced**: Exact squad size (11), position quotas (4G, 4F, 2C, 1HC), club quotas (max 6 court players per club), and salary cap (100.0 Cr), respecting locked and excluded players.

### Explicit Objective vs Strategic Multi-Round Scope
- **Current V0.5 Scope**: Immediate **Round 1 Expected Score Maximization** under salary cap and squad legality rules. It solves the starting squad for the immediate opening round.
- **Distinction from Future Strategic Draft**: A multi-round strategic initial-team optimizer (evaluating trade liquidity, scheduled double-weeks, and unlimited transfer windows across Rounds 1–6 via beam search) is intentionally deferred to **V0.5.x / V0.6**. Recommendations are clearly labeled by their objective and never claimed to be universally optimal across the entire season.

### Reliable Audit Logging
- Every team created with an initial squad triggers a mandatory `INITIAL_TEAM` decision record in `DecisionStore`.
- Any failure during decision logging raises an error and transactionally rolls back team creation, guaranteeing no team exists without its historical audit trail.

> **Critical boundary:** V0.5 adds usability and workflow around the quantitative engine. It must not replace or weaken the deterministic rules, validated predictions, or optimizer underneath it.
