# V0.4 — Fantasy Decision & Optimization Layer

> **Status:** Planned  
> **Prerequisite:** V0.3 validated predictive projection layer.  
> **Core boundary:** **V0.3 predicts. V0.4 decides.**

## 1. Objective

Turn V0.3 projections into optimal fantasy decisions under the actual EuroLeague Fantasy rules and constraints.

```text
V0.3 projections
  ├─ expected FP
  ├─ uncertainty
  ├─ P(play)
  ├─ expected minutes
  └─ value
        ↓
Decision engine
  ├─ legal lineup
  ├─ formation
  ├─ captain
  ├─ sixth man
  ├─ bench
  ├─ transfers
  └─ future-round planning
        ↓
Historical decision backtest
        ↓
Oracle regret
```

## 2. Success criteria

- [ ] Clean V0.3 → optimizer interface.
- [ ] Explicit fantasy constraints.
- [ ] Deterministic optimal legal lineup.
- [ ] Joint captain/sixth-man/bench/formation optimization.
- [ ] Single-round transfer optimization.
- [ ] Historical decision backtesting.
- [ ] Oracle regret evaluation.
- [ ] No future-information leakage.
- [ ] Deterministic, reproducible results.
- [ ] Multi-round optimization only after single-round correctness is established.

## 3. Architecture principles

### Prediction and optimization remain separate

The optimizer consumes a projection contract such as:

```python
PlayerProjection(
    player_id,
    expected_fp,
    probability_play,
    expected_minutes,
    fp_per_minute,
    uncertainty,
    price,
    position,
    team_id,
)
```

It must not know how the prediction was generated. This permits:

```text
xPDK → optimizer
EWMA → optimizer
V0.3 model → optimizer
future model → optimizer
```

without rewriting optimization logic.

### Optimize the real fantasy objective

The objective must account for:

- captain multiplier;
- sixth-man rules;
- bench multipliers;
- formations;
- roster/club limits;
- budget;
- transfer rules.

Do not optimize raw `sum(expected_fp)` when the fantasy scoring rules imply a different objective.

### Separate value from risk

Start with expected score. Add risk-aware modes only after the deterministic optimizer is correct and V0.3 uncertainty is validated.

## 4. Phase A — Formalize constraints

Create a deterministic constraint layer covering:

- squad;
- available players;
- prices;
- positions;
- club;
- round;
- budget;
- transfers;
- projections;
- fantasy rules.

Every constraint must be explicit and testable.

## 5. Phase B — Fixed-squad lineup optimizer

First milestone:

```text
fixed squad
  ↓
optimize formation
  + lineup
  + captain
  + sixth man
  + bench
```

### Objective

Maximize expected fantasy score using the deterministic fantasy scoring rules.

### Search method

For a fixed 11-player squad, exhaustive enumeration may remain entirely adequate.

Do not introduce ILP/CP-SAT simply because the problem is an optimization problem.

Use a solver only when profiling shows the search space requires it.

## 6. Phase C — Joint decisions

Captain, sixth man and bench must be optimized jointly with the lineup.

Do not assume:

```text
best lineup + best captain
```

equals:

```text
best joint lineup/captain decision
```

The same applies to sixth man and bench.

## 7. Phase D — Formation

Represent formations as constraints rather than hard-coded optimizer branches.

The optimizer should enumerate legal formations and compare their expected scores.

This keeps rule changes isolated from optimization code.

## 8. Phase E — Current-squad CLI

Initial command:

```powershell
elf optimize lineup --season 2026 --round 1
```

Output:

- recommended lineup;
- formation;
- captain;
- sixth man;
- bench;
- projected score;
- uncertainty;
- meaningful alternatives.

Expose the objective value so decisions are auditable.

## 9. Phase F — Transfer optimization

After fixed-squad optimization is stable, add single-round transfers.

Inputs:

```text
current squad
available market
prices
budget
transfer rules
V0.3 projections
```

For each candidate transfer set:

```text
new squad
  ↓
optimal lineup
  ↓
projected score
```

Compare with the optimized current squad.

Initial transfer value:

```text
transfer value =
new optimal score
-
current optimal score
-
transfer cost
```

Keep the first version single-round.

## 10. Phase G — Candidate generation

Transfer search can become combinatorial.

Candidate filtering may use:

- expected FP;
- expected value;
- availability;
- position;
- price;
- club limits;
- replacement quality.

But filtering must be measurable.

Keep an exhaustive mode for small problems so candidate generation can be validated against the true optimum.

## 11. Phase H — Multi-round optimization

Only after single-round transfers are correct.

Start with horizon:

```text
N = 2
```

then:

```text
N = 3
N = 4
```

Objective:

```text
maximize expected total fantasy score
```

subject to:

- roster constraints;
- transfer rules;
- budget;
- availability;
- formations;
- captaincy;
- legitimately knowable future information.

Do not start with a full-season optimizer.

## 12. Phase I — Risk-aware optimization

Expose configurable modes.

### Expected value

```text
maximize E[score]
```

### Conservative

```text
maximize E[score] - λ × risk
```

### Aggressive

Allow greater variance when chasing upside.

Do not encode a subjective “best” strategy into the default. Expose the trade-off.

## 13. Phase J — Value above replacement

Use V0.3 projections to compute:

```text
surplus_value =
expected_fp
-
replacement_expected_fp
```

Support positional replacement where appropriate.

Use this as an input to transfer analysis, not as a replacement for the actual fantasy objective.

## 14. Phase K — Option value

Formalize the V0.2 option-value concept.

For short horizons:

```text
transfer value =
immediate expected gain
+ future option value
- transfer cost
```

Initially use a transparent deterministic/heuristic implementation.

More sophisticated stochastic planning can come later.

## 15. Phase L — Historical decision backtesting

For every historical round:

```text
information available before round
        ↓
V0.3 predictions
        ↓
V0.4 optimizer
        ↓
historical decision
        ↓
actual result
        ↓
oracle comparison
```

Compare with:

- V0.2 optimizer;
- simple heuristic lineup;
- random legal baseline where useful;
- oracle lineup.

Use oracle regret as a primary decision-quality metric.

## 16. Decision metrics

### Lineup

- selected score;
- oracle score;
- lineup regret.

### Captain

- selected captain score;
- oracle captain score;
- captain regret.

### Sixth man

- selected score;
- oracle score;
- regret.

### Bench

- bench contribution;
- oracle contribution;
- regret.

### Formation

- selected formation score;
- best legal formation score;
- regret.

### Transfers

- immediate gain;
- transfer cost;
- net gain;
- future-round gain;
- cumulative regret.

## 17. Robustness

Handle:

- unavailable players;
- zero/missing prices;
- duplicate players;
- invalid formations;
- insufficient eligible players;
- club-limit violations;
- tied projections;
- tied scores;
- missing projections;
- extreme uncertainty;
- empty candidate sets.

Tie-breaking must be deterministic.

## 18. Optimization correctness

For small artificial squads, compare the optimizer against exhaustive enumeration:

```text
optimizer result == true exhaustive optimum
```

If a faster solver is introduced later:

```text
solver result == exhaustive result
```

on small reference cases.

This is a core correctness test.

## 22. Recommended implementation order

1. Formalize all rules and constraints.
2. Build fixed-squad optimizer.
3. Build exhaustive correctness fixtures.
4. Integrate V0.3 projections.
5. Backtest historical lineups.
6. Build single-round transfer optimizer.
7. Backtest transfers.
8. Add candidate-generation optimization while preserving exactness.
9. Add 2–4 round planning.
10. Add risk-aware decisions.
11. Add option value.
12. Introduce faster solvers only when profiling requires them.

## 23. Explicitly out of scope

Do not combine V0.4 with:

- LLM strategy generation;
- GUI;
- automatic account interaction;
- live scraping;
- social/news sentiment;
- deep-learning prediction;
- reinforcement learning;
- full-season stochastic optimization;
- autonomous transfer execution.

V0.4 is the **correct, measurable deterministic decision engine**.

## 25. Definition of done

V0.4 is complete when we can demonstrate:

> Given exactly the information available before a historical round, V0.3 produces projections, V0.4 converts them into a legal fantasy decision, and that decision can be compared rigorously with the historical oracle.

The evaluation loop is:

```text
historical information
        ↓
V0.3 prediction
        ↓
V0.4 optimization
        ↓
legal fantasy decision
        ↓
actual historical outcome
        ↓
oracle comparison
        ↓
regret
```
